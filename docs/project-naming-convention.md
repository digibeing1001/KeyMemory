# 项目命名规范

本规范定义 KeyMemory 中"项目"（Project）的命名规则，目标是让项目名称既符合人类在公司机构中的实际命名习惯，又方便智能体（Agent）解析、检索和匹配。

## 设计依据

本规范参考了真实公司机构的项目命名实践：

- **产品/系统命名**：直接使用产品名（如 KeyMemory、Slack、Notion）
- **部门+项目命名**：组织维度+具体项目（如"支付团队/订单中台"）
- **客户+项目命名**：客户名+项目内容（如"某银行/核心系统升级"）
- **功能描述命名**：用功能描述项目（如"用户画像系统"、"数据分析平台"）
- **层级化命名**：父项目是组织/领域，子项目是具体交付物

## 命名公式

### 公式 1：产品/系统直命名

适用于独立产品、工具、系统。

```
<产品名>
```

**示例**：
- `KeyMemory`
- `个人博客`
- `简历系统`
- `读书笔记`

### 公式 2：组织+项目

适用于公司、团队内部的多项目场景。父项目是组织，子项目是具体项目。

```
<组织/团队> / <项目名>
```

**示例**：
```
支付团队
├── 订单中台
├── 退款系统
└── 对账平台

增长团队
├── 用户画像
└── 推荐系统
```

### 公式 3：领域+项目

适用于按业务领域组织的场景。父项目是领域，子项目是具体项目。

```
<业务领域> / <项目名>
```

**示例**：
```
前端
├── 官网改版
├── 后台管理系统
└── 移动端 App

基础设施
├── CI/CD 流水线
├── 监控系统
└── 日志平台
```

### 公式 4：客户+项目

适用于乙方为甲方做项目的场景。

```
<客户名> / <项目名>
```

**示例**：
```
某银行
├── 核心系统升级
└── 移动银行 App

某电商
├── 数据中台
└── 搜索系统
```

## 命名原则

### 1. 具体优先于通用

项目名应指向一个具体的对象、产品、任务或领域，而非一个类别、状态或动作。

| 好 | 坏 | 原因 |
|---|---|---|
| KeyMemory | 项目 | "项目"是类别，不是具体对象 |
| 订单中台 | 工作 | "工作"过于宽泛 |
| Q3 财报分析 | 文档 | "文档"是类型，不是项目 |
| 用户画像系统 | 开发 | "开发"是动作，不是对象 |
| 博客迁移计划 | 临时 | "临时"是状态，会随时间失效 |

### 2. 稳定优先于临时

项目名应能在较长时间内保持有效，避免使用会过期的信息。

| 好 | 坏 | 原因 |
|---|---|---|
| 个人博客 | 2024年博客 | 年份会过期 |
| 读书笔记 | 本月阅读 | "本月"会失效 |
| 简历系统 | v2 重构 | 版本号会迭代 |

### 3. 可读优先于可编码

项目名是给人看的，不是给编译器看的。使用自然语言而非编程标识符。

| 好 | 坏 | 原因 |
|---|---|---|
| 订单中台 | order_platform | 下划线编程风格 |
| 用户画像 | UserProfile | 驼峰编程风格 |
| Q3 财报 | q3finance | 无分隔，难读 |

### 4. 名实一致

项目名应与该项目下的记忆内容主题一致。如果记忆内容偏离项目名，说明：
- 项目名需要更新
- 记忆应该归类到其他项目
- 需要创建新项目

## 字符规范

### 允许的字符

- **中文**：汉字、中文标点（顿号、书名号等）
- **英文**：大小写字母、数字、连字符（`-`）、空格
- **符号**：点（`.`）、括号（`()`）、冒号（`:`）用于版本或子项标注
- **其他**：Unicode 文字（日文、韩文等）

### 禁止的字符

- **路径分隔符**：`/`、`\`（会与项目路径冲突）
- **控制字符**：换行、制表符等
- **特殊符号**：`<`、`>`、`|`、`*`、`?`、`"`（文件系统不兼容）
- **编程前缀**：不以 `.`、`-`、`_` 开头

### 长度规范

- **最短**：中文 ≥ 2 字，英文 ≥ 4 字符
- **最长**：≤ 64 字符（超出会被截断显示）
- **推荐**：4-20 字符，足够具体又不冗长

## 层级规范

项目支持父子层级（通过 `parentId` 建立）。层级路径用 `/` 分隔，存储在 `path` 字段。

### 层级深度

- **推荐**：≤ 3 层（如 `公司/产品线/KeyMemory`）
- **最大**：≤ 5 层（超过会让导航和检索变复杂）

### 层级命名规则

- **父项目**：使用组织、团队、领域或客户名（如"支付团队"、"前端"、"某银行"）
- **子项目**：使用具体项目名（如"订单中台"、"官网改版"、"核心系统升级"）
- **避免**：同一层级下出现语义重复（如"项目/KeyMemory 项目"）

### 层级路径示例

```
个人项目
├── KeyMemory
│   ├── 文档站点
│   └── CLI 工具
├── 个人博客
└── 读书笔记

工作
├── 支付团队
│   ├── 订单中台
│   │   ├── 支付模块
│   │   └── 退款模块
│   └── 对账系统
└── 增长团队
    ├── 用户画像
    └── 推荐系统

客户项目
├── 某银行
│   ├── 核心系统升级
│   └── 移动银行 App
└── 某电商
    └── 数据中台
```

## 语言规范

### 单语言优先

项目名应使用单一语言，不混用中英文（除非是专有名词）。

| 好 | 坏 | 原因 |
|---|---|---|
| 订单中台 | 订单Platform | 中英混用难读 |
| Order Platform | Order 中台 | 中英混用难读 |
| KeyMemory | Key 记忆 | KeyMemory 是专有名词可保留 |

### 专有名词保留

技术专有名词、产品名、品牌名保留原文，不强制翻译。

- **保留**：KeyMemory、React、TypeScript、OpenAI、GPT-4
- **翻译**：Order Platform → 订单平台（如果是中文项目）

## Agent 解析友好性

### 命名可预测性

Agent 通过项目名进行语义匹配和检索。命名应让 Agent 能：

1. **从名称推断内容**：看到"订单中台"就知道是订单相关记忆
2. **区分不同项目**：不会把"订单中台"和"订单分析"混淆
3. **建立关联**：能识别"订单中台/支付模块"是订单中台的子项目

### 避免歧义

- **不用缩写**：用"用户界面"而非"UI"（除非缩写是行业通用）
- **不用代号**：用"支付模块"而非"模块A"
- **不用编号**：用"简历系统"而非"项目001"
- **不用内部梗**：用"数据分析平台"而非"阿波罗计划"

### 与记忆内容一致

项目名应与该项目下的记忆内容主题一致。当 agent 写入记忆时，应选择与记忆内容最匹配的项目；如果找不到合适项目，应提示用户创建新项目而非强行归类。

## 通用名黑名单

以下名称过于通用，系统会判定为"非具体项目名"，不作为整理建议的候选：

**中文**：未分类、工作、学习、笔记、临时、杂项、其他、其它、默认、全部、所有、日常、琐事、事项、内容、资料、文档、记录、想法、灵感、待办、任务

**英文**：uncategorized、unclassified、default、general、global、misc、miscellaneous、migrated、memory、memories、notes、note、temp、tmp、test、tests、testing、dev、devel、develop、development、src、source、lib、libs、bin、build、docs、doc、work、works、study、learning、learn、projects、project、stuff、things、other、others、all、inbox、draft、drafts、archive、archived

## 验证规则

系统在创建项目时会进行以下验证：

1. **非空**：项目名不能为空
2. **长度**：中文 ≥ 2 字，英文 ≥ 4 字符
3. **字符**：不含禁止字符
4. **通用名检测**：通用名会被标记，不参与整理建议
